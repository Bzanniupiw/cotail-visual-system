# CoTail Runtime Console 操作手册

本文档面向第一次使用本系统的用户。你可以把它当作“从启动服务、选择 GPU、发请求、采集实验、分析 CPTI、执行保护策略”的完整操作说明。

## 1. 系统是做什么的

CoTail Runtime Console 是一个面向共享 GPU 服务器的实时监控与动态诊断系统。它解决的问题是：

- 服务器上有多张 GPU，比如 8 张 RTX 4090。
- 你希望选择空闲 GPU 启动 vLLM / SGLang / llama.cpp 服务。
- 同时服务器上可能存在 CPU 共置负载，比如 stress-ng、nginx、redis、ffmpeg、kernel build 等。
- 这些 CPU 负载可能拖慢单 GPU LLM 服务，尤其是 TTFT、TPOT、尾部延迟。
- 系统通过 Baseline / Co-location / Protected 三阶段采集，再结合微观 NVTX/CPTI trace，判断干扰来源，并推荐保护策略。

系统分为 5 个页面：

1. **实时监控**：看 GPU、进程、托管作业，启动大模型服务，发请求和压测。
2. **自动诊断**：采集宏观三阶段指标，验证负载和保护策略对 throughput / TTFT / TPOT 的影响。
3. **微观 CPTI**：导入 Nsight SQLite trace，计算核心阶段的 P95/P99 放大和 CPTI。
4. **策略流**：展示 CoTail 决策流程、CTS 验证盘，并支持人工策略覆盖。
5. **租户成本**：查看共置 CPU 租户、保护策略成本和诊断开销。

## 2. 启动与访问

进入项目目录：

```bash
cd /path/to/cotail_visual_system
```

启动服务：

```bash
python -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8899
```

浏览器访问：

```text
http://127.0.0.1:8899
```

如果是在远程 Linux 服务器上运行，可以使用 SSH 端口转发：

```bash
ssh -L 8899:127.0.0.1:8899 user@server
```

然后在本地浏览器打开 `http://127.0.0.1:8899`。

## 3. 最推荐的完整使用流程

第一次使用时，按这个顺序最稳：

1. 打开 **实时监控**，确认 GPU 状态。
2. 如果还没有 LLM 服务，在 **动态调度启动** 里启动 vLLM。
3. 在 **大模型请求与压测** 里点“检查模型”，确认服务可用。
4. 在 **自动诊断** 里依次采集：
   - Baseline：无 CPU 干扰。
   - Co-location：启动 CPU 负载后采集。
   - Protected：执行保护策略后采集。
5. 看三阶段卡片和性能变化视图，确认宏观上是否存在干扰和恢复。
6. 使用 Nsight 抓取 Baseline / Co-location / Protected trace，得到 SQLite 文件。
7. 在 **微观 CPTI** 页面解析 SQLite，生成 CoTail 诊断。
8. 到 **策略流** 页面看推荐策略、CTS 和人工控制台。
9. 到 **租户成本** 页面看后台负载和保护策略对共置租户的成本。

注意：**自动诊断页只负责宏观指标，不生成正式 CPTI 结论。正式 CoTail 诊断必须在微观 CPTI 页面完成。**

## 4. 实时监控页面

### 4.1 顶部指标

- **Host**：当前服务器主机名。
- **CPU**：整机 CPU 使用率或核心数。
- **Memory**：内存占用比例。
- **Idle GPU**：系统根据显存、GPU util、计算进程数量选出的空闲 GPU。
- **Jobs**：当前由系统托管的大模型服务或 CPU 负载数量。

### 4.2 GPU 实时状态

每张 GPU 会显示：

- **Util**：GPU 计算利用率。越高说明越忙。
- **Temp**：温度。
- **Memory**：已用显存 / 总显存。
- **Free**：剩余显存。
- **Power**：当前功耗 / 功耗上限。
- **Proc**：计算进程数量。
- **IDLE / BUSY / WARM**：
  - `IDLE`：比较适合启动新服务。
  - `BUSY`：已有计算进程，不建议占用。
  - `WARM`：没有明显计算进程，但可能还有负载或显存占用。

### 4.3 动态调度启动

这个模块用于启动 LLM 服务，默认模拟你常用的命令：

```bash
CUDA_VISIBLE_DEVICES=1 vllm serve /home/liguowei/models/deepseek-7b --port 8102 --gpu-memory-utilization 0.7 --max-model-len 8192 --enforce-eager
```

字段说明：

- **模型路径**：模型所在目录，例如 `/home/liguowei/models/deepseek-7b`。
- **后端**：可选 `vllm`、`sglang`、`llama-server`。
- **自动选 GPU**：勾选后系统自动选择空闲 GPU。
- **手动 GPU**：如果不想自动选，在这里填 GPU 编号，例如 `1`。
- **端口**：服务监听端口，例如 `8102`。
- **GPU memory util**：vLLM 显存利用率，例如 `0.7`。
- **max model len**：最大上下文长度，例如 `8192`。
- **enforce eager**：对应 vLLM 的 `--enforce-eager`。
- **CPU workload**：是否同时启动一个 CPU 共置负载。一般启动 LLM 服务时选 `none`。
- **CPU cores**：CPU 负载绑定核心，例如 `0-60,128-188`。
- **workers**：CPU 负载 worker 数。
- **min free MiB**：自动选 GPU 时要求的最低空闲显存。
- **max util %**：自动选 GPU 时允许的最高 GPU 利用率。
- **extra args**：额外传给服务的参数，例如 `--trust-remote-code`。
- **dry-run**：非常重要。勾选时只生成命令，不真实启动。取消勾选后才会启动服务。

按钮：

- **生成/启动**：
  - dry-run 勾选：只展示将要执行的命令。
  - dry-run 取消：真正启动服务和可选 CPU 负载。

结果判断：

- 如果启动成功，托管作业表中会出现新 job。
- 如果 API 显示 `OPEN`，说明端口已经可访问。
- 如果启动失败，查看 `launch-output` 或托管作业的 `Logs`。

### 4.4 GPU 进程

显示 `nvidia-smi` 里的进程信息：

- **GPU**：进程所在 GPU。
- **PID**：进程 ID。
- **Type**：进程类型，通常 `C` 是计算进程。
- **User**：用户。
- **Memory**：该进程占用显存。
- **Process**：进程名。

用途：

- 确认某张卡是否真的空闲。
- 找到 vLLM、Python、llama-server 等进程。

### 4.5 大模型请求与压测

字段：

- **API base**：OpenAI 兼容接口地址，例如 `http://127.0.0.1:8102/v1`。
- **model**：模型名或模型路径。
- **max tokens**：每个请求最多生成 token 数。
- **concurrency**：并发请求数，也就是同时在飞的请求数量。它不是模型内部 batch size，但会促使服务端形成动态 batch。
- **requests**：本轮压测总请求数。
- **temperature**：采样温度。
- **prompt**：请求输入文本。

按钮：

- **检查模型**：请求 `/v1/models`，确认服务是否可访问。
- **单次请求**：发送一个请求，用于快速验证模型能否返回。
- **并发压测**：发送 `requests` 个请求，并保持最多 `concurrency` 个请求同时执行。

指标：

- **Success**：成功请求数 / 总请求数。
- **TTFT avg**：平均首 token 延迟。越低越好。
- **TPOT avg**：平均每输出 token 时间。越低越好。
- **Throughput**：总生成 token 数 / 总 wall time，单位 tok/s。越高越好。
- **Latency**：平均请求总耗时。

### 4.6 托管作业

显示系统启动过的服务或 CPU 负载。

按钮：

- **刷新作业**：重新读取作业状态。
- **Use**：把该 LLM job 的 API 地址、模型和端口填入请求、自动诊断、策略控制相关表单。
- **Logs**：查看该 job 的 stdout/stderr 日志。
- **Stop**：停止该 job。

注意：CPU 负载 job 没有 `Use`，因为它不是 LLM 服务。

## 5. 自动诊断页面

自动诊断页负责宏观三阶段实验，不负责正式 CPTI。

### 5.1 三阶段含义

- **Baseline**：没有共置 CPU 负载时的 LLM 性能。
- **Co-location**：引入 CPU 负载后的 LLM 性能。
- **Protected**：引入 CPU 负载，并执行保护策略后的 LLM 性能。

公平比较的原则：

- Baseline、Co-location、Protected 的模型、端口、prompt、requests、concurrency、max tokens 应一致。
- 勾选 `Fix vLLM CPU placement` 后，系统会把 vLLM 固定到同一组 `NUMA vLLM` 核心，避免服务端 CPU 放置漂移。
- Co-location 和 Protected 应使用相同类型和强度的 CPU 负载。

### 5.2 Canary 请求参数

- **API base**：LLM 服务地址。
- **model**：模型路径或模型名。
- **requests**：本轮总请求数。
- **concurrency**：同时在飞请求数。通常可理解为压测并发度，和 batch_size 接近，但不是 vLLM 内部真实 batch size。
- **max tokens**：每个请求最大输出 token 数。
- **执行 canary 请求**：勾选后真实请求 LLM；取消后只采样系统资源，不压测模型。
- **canary prompt**：测试 prompt。
- **repeat_times**：生成长 prompt 时的重复次数。

按钮：

- **生成长 Prompt**：自动生成较长输入，使 TTFT 更接近旧实验脚本。

### 5.3 Co-location 负载

字段：

- **负载类型**：
  - `stress-ng`：强 CPU 计算压力，最容易制造明显干扰。
  - `nginx`：网络/连接类负载，不一定显著影响 LLM。
  - `redis`、`memcached`：内存/网络请求压力。
  - `ffmpeg`、`7zip`、`openssl`：计算型或编码/压缩类压力。
  - `kernel_build`：编译压力，可能很快结束。
  - `zstd-compress`、`sqlite-txn`、`image-preprocess`、`text-search`：不同类型的数据处理压力。
- **CPU cores**：共置负载绑定在哪些 CPU 核上。
- **workers**：负载 worker 数。
- **duration s**：负载持续时间。
- **采集前启动负载**：采集 Co-location 时自动启动负载。
- **负载 dry-run**：只生成负载命令，不实际启动。

按钮：

- **启动负载**：按当前配置启动一个 CPU 负载。
- **停止当前**：停止当前由自动诊断页启动的负载。
- **检测当前负载**：判断当前负载是否真的产生 CPU/CTX/I/O 压力。
- **停止全部托管负载**：停止系统管理的全部 CPU 负载。
- **扫描遗留负载**：查找之前启动但没有关闭的 stress-ng、nginx、redis 等负载。
- **清理遗留负载**：终止扫描到的遗留负载。
- **一键探测全部负载**：依次启动并检测所有内置负载，看哪些能在当前服务器上产生有效压力。
- **dry-run**：用于一键探测全部负载时只预演，不真实启动。

负载健康结果：

- **strong**：负载正在运行，并产生明显压力。
- **weak**：负载存在，但压力不明显。
- **exited**：负载已经退出。
- **missing**：没有检测到该负载。

注意：`strong` 只表示负载活跃，不代表一定会影响 LLM。比如 nginx 可能 strong，但 TPOT 影响只有 1%-2%。

### 5.4 Protected 保护措施

字段：

- **保护策略**：
  - `rt`：给 EngineCore / busy TID 设置实时调度优先级，适合 scheduler 或 batch 构造被抢占的情况。
  - `numa`：把 vLLM 和共置负载放到不同 NUMA/core 区域，适合拓扑或缓存压力。
  - `rt+numa`：同时使用 RT 和 NUMA 隔离，适合强干扰。
  - `nice`：调整进程 nice 值。
  - `cgroup`：生成 cgroup 权重隔离计划。
  - `none`：不执行保护。
- **服务端口**：用于扫描 vLLM 服务。
- **vLLM PIDs**：vLLM 服务进程 ID，可自动扫描。
- **EngineCore TID**：要设置 RT 的线程 ID，可自动识别。
- **Battle cores**：默认共置负载压力区。
- **NUMA vLLM**：vLLM 固定核心。
- **NUMA co-tenant**：共置负载隔离核心。
- **RT priority**：实时调度优先级。
- **Fix vLLM CPU placement**：采集每个阶段前固定 vLLM CPU affinity，建议保持勾选。
- **Protected 前执行策略**：勾选后，在采集 Protected 前真实执行保护策略。

按钮：

- **扫描服务**：根据端口发现 vLLM 进程 PID。
- **识别 TID**：从 vLLM 进程中识别最忙线程，通常用于 EngineCore RT。
- **采集 Baseline**：停止本系统启动的共置负载，固定 vLLM 放置，然后采集基线。
- **采集 Co-location**：启动 CPU 负载并采集受干扰性能。
- **采集 Protected**：按策略执行保护后采集性能。

### 5.5 三阶段卡片怎么看

每张卡片含义：

- **状态**：本阶段请求是否成功。
- **Throughput**：吞吐，越高越好。
- **TTFT**：首 token 延迟，越低越好。
- **TPOT**：每 token 解码时间，越低越好。
- **CPU**：采集期间 CPU 压力。
- **CTX**：上下文切换次数，过高可能说明调度压力大。
- **I/O**：磁盘和 loopback I/O。
- **Load cores**：共置负载所在 CPU 核。
- **vLLM cores**：vLLM 实际绑定 CPU 核。
- **Placement**：是否固定了 vLLM CPU 放置。
- **负载**：本阶段使用的共置负载。
- **保护**：本阶段使用的保护策略。
- **保护执行**：
  - `dry-run / 未执行`：只是预演，没有真实修改进程。
  - `已验证`：保护动作执行并验证成功。
  - `失败`：执行失败，需要看错误信息。
- **负载活跃度**：负载健康状态和 CPU 压力。
- **LLM 影响**：相对 Baseline 的 TPOT 增加和吞吐下降。
- **诊断开销**：本轮 canary 压测带来的估计开销、耗时和请求数。

### 5.6 宏观结果怎么判断

先看 Co-location：

- 如果 TPOT 增加很小，比如 1%-5%，说明该负载对 LLM 影响不明显。
- 如果 TPOT 增加几十到几百个百分点，说明存在明显干扰。
- 如果 Throughput 大幅下降，说明整体服务能力被拖慢。
- 如果 TTFT 增加明显，可能是 prefill、排队或调度受阻。

再看 Protected：

- 如果 TPOT 从高值恢复到接近 Baseline，说明保护策略有效。
- 如果 Throughput 也恢复，说明整体效果很好。
- 如果 TPOT 恢复但 Throughput 仍低，说明尾部解码已恢复，但整体资源或队列仍有压力。
- 如果 Protected 比 Co-location 更差，说明策略没有覆盖瓶颈，或 CPU 放置/负载清理不干净。

## 6. 微观 CPTI 页面

这个页面负责正式 CoTail 微观诊断。

### 6.1 CPTI 是什么

CPTI 衡量 CPU 共置干扰对 vLLM 核心服务阶段尾部延迟的放大程度。它依赖四个核心阶段的 P95/P99：

- `scheduler.step`
- `batch.construct`
- `model.execute`
- `model.forward`

系统会比较：

- Baseline trace：无干扰。
- Co-location trace：有干扰。
- Protected trace：有干扰并开启保护，可选。

### 6.2 输入文件

- **Baseline SQLite**：Baseline 阶段 Nsight SQLite。
- **Co-location SQLite**：Co-location 阶段 Nsight SQLite。
- **Protected SQLite**：Protected 阶段 Nsight SQLite，可选，但建议提供。

按钮：

- **解析 Baseline**：读取 baseline sqlite 中的 NVTX 阶段事件。
- **解析 Co-location**：读取 co-location sqlite。
- **解析 Protected**：读取 protected sqlite。
- **生成 CoTail 诊断**：用已解析阶段数据生成正式风险、CPTI、策略和决策。
- **刷新微观诊断**：刷新当前页面上的 CPTI 可视化。

### 6.3 阶段可视化怎么看

每个阶段会显示三条：

- **Baseline P95/P99**
- **Co-location P95/P99**
- **Protected P95/P99**

如果 Co-location 条明显长于 Baseline，说明该阶段被干扰放大。

如果 Protected 条明显缩短，说明保护策略抑制了该阶段尾部放大。

### 6.4 Dominant Stage 怎么解释

- **scheduler.step 主导**：调度循环被 CPU 抢占，优先考虑 `rt`。
- **batch.construct 主导**：batch 构造受阻，也优先考虑 `rt`。
- **model.execute 主导**：执行路径受到系统调度或资源争用影响，可能需要 `rt` 或 `rt+numa`。
- **model.forward 主导**：更可能和拓扑、缓存、NUMA、CPU/GPU 协同压力有关，优先考虑 `numa` 或 `rt+numa`。

## 7. 策略流页面

策略流页面展示正式 CoTail 诊断结果和人工干预入口。

### 7.1 CoTail Live Workflow

流程节点：

1. **硬件特征抓取**：采集 CPU、CTX、I/O、拓扑等风险特征。
2. **风险评估**：判断是否存在共置风险。
3. **NVTX Trace 与 CPTI**：计算微观阶段尾部放大。
4. **策略推荐**：根据主导瓶颈推荐策略。
5. **SLO 与 CTS 验证**：判断保护后是否满足部署要求。

节点变亮表示该步骤已经完成或正在进行。

### 7.2 顶部诊断指标

- **Risk**：风险级别。
- **CPTI**：平均核心阶段尾部放大比例。
- **Dominant Stage**：主导瓶颈阶段。
- **Policy**：推荐策略。
- **Decision**：最终部署决策。

常见决策：

- **DIRECT_COLOCATE**：可以直接共置，不需要保护。
- **PROTECTED_COLOCATE**：需要保护策略，共置可接受。
- **PROTECTED_COLOCATE_WARN**：尾部已恢复，但某些严格 SLO 仍略超，需要谨慎。
- **REJECT_COLOCATION**：保护后仍不满足要求，不建议共置。
- **NEEDS_VALIDATION**：还缺少 Protected 或验证数据。

### 7.3 CTS 验证盘

CTS 表示核心尾部抑制率：

```text
CTS = 1 - Protected_CPTI / Co-location_CPTI
```

理解方式：

- 接近 100%：保护策略几乎完全抑制尾部放大。
- 50%-80%：有明显效果，但还可以优化。
- 小于 50%：效果较弱。
- 小于等于 0：保护无效或更差。

### 7.4 Manual Override

这里可以人工生成或执行策略计划。

策略按钮：

- **RT**：选择实时调度策略。
- **NUMA**：选择 NUMA 隔离。
- **RT+NUMA**：组合策略。
- **nice**：nice 优先级策略。
- **cgroup**：cgroup 权重策略。
- **none**：不保护。

字段：

- **policy**：当前策略名。
- **service ports**：要扫描的服务端口。
- **vLLM PIDs**：目标 vLLM 进程。
- **EngineCore TID**：目标线程。
- **Battle cores**：干扰压力核心。
- **NUMA vLLM**：vLLM 应绑定核心。
- **NUMA co-tenant**：共置负载应绑定核心。
- **RT priority**：RT 优先级。

按钮：

- **扫描服务**：自动填入 vLLM PIDs。
- **识别 TID**：自动填入 EngineCore/busy TID。
- **生成策略计划**：dry-run，只展示计划，不执行。
- **执行策略**：真实修改进程 affinity / nice / RT 调度。

注意：执行策略会真实影响服务器进程，请确认 PID 和 TID 正确。

## 9. 常见问题

### 9.1 dry-run 是什么意思

dry-run 就是“只预演，不执行”。

- 启动服务 dry-run：只生成命令，不启动 vLLM。
- 负载 dry-run：只生成负载命令，不启动负载。
- 策略 dry-run：只展示将要执行的保护动作，不修改进程。

如果你发现点击按钮后没有真实进程，先检查 dry-run 是否还勾着。

### 9.2 为什么 nginx strong，但 LLM 几乎没变差

`strong` 只表示 nginx 活跃，不表示它一定会干扰 LLM。不同负载的干扰路径不同：

- stress-ng 更容易造成 CPU 调度抢占。
- nginx 可能更多是网络连接和轻量请求，未必拖慢 vLLM。
- redis/memcached 可能影响内存和 loopback。

所以判断干扰要看 LLM 的 TPOT、TTFT、Throughput，而不是只看负载 strong。

### 9.3 为什么 Protected 还是差

常见原因：

- 保护策略没勾选真实执行。
- vLLM PIDs 或 EngineCore TID 没识别到。
- 负载没有关闭，存在多个遗留 stress-ng。
- 纯 RT 只保护调度线程，不能解决 NUMA/缓存/整体 CPU 饱和。
- 需要改用 `rt+numa`。

建议先做：

1. 扫描遗留负载。
2. 清理遗留负载。
3. 勾选 Fix vLLM CPU placement。
4. 用相同参数重采 Baseline / Co-location / Protected。

### 9.4 requests 和 concurrency 怎么理解

- `requests` 是本轮总请求数。
- `concurrency` 是同时执行的请求数。

例如：

```text
requests = 64
concurrency = 16
```

表示总共发 64 个请求，最多同时跑 16 个。

它不是 vLLM 内部真实 batch size，但并发越大，服务端越可能形成更大的动态 batch。

### 9.5 TTFT 为什么有时很小，有时几百毫秒

TTFT 受这些因素影响：

- prompt 长度。
- concurrency。
- prefill 负载。
- 队列等待。
- 模型大小和 max model len。
- GPU 是否已有其他进程。

如果想复现实验中几百毫秒的 TTFT，应使用较长 prompt，并保持固定 concurrency 和 requests。

### 9.6 自动诊断为什么没有 CPTI

因为 CPTI 是微观阶段指标，需要 Nsight/NVTX trace 的 P95/P99 数据。

自动诊断只有宏观 canary 指标，不能直接算正式 CPTI。

正确流程是：

```text
自动诊断采集宏观三阶段
-> Nsight 抓 trace
-> 微观 CPTI 页面解析 SQLite
-> 生成 CoTail 诊断
-> 策略流页面看结果
```

## 10. 推荐实验模板

### 10.1 验证 stress-ng 干扰和 RT 效果

1. 实时监控页确认服务可用。
2. 自动诊断页生成长 prompt。
3. 设置：
   - requests = 32
   - concurrency = 32
   - max tokens = 512
   - workload = stress-ng
   - workers = 60
   - Load cores = `0-60,128-188`
   - NUMA vLLM = `0-63,128-191`
   - Fix vLLM CPU placement = 勾选
4. 采集 Baseline。
5. 采集 Co-location。
6. 保护策略选 `rt`，扫描服务，识别 TID，勾选 Protected 前执行策略。
7. 采集 Protected。
8. 看 TPOT 是否从 Co-location 明显恢复。
9. 抓三阶段 Nsight trace，在微观 CPTI 页面生成正式诊断。

### 10.2 验证 RT+NUMA 效果

1. Load cores 设置为 battle cores。
2. NUMA vLLM 设置为 GPU 本地核心。
3. NUMA co-tenant 设置为远端核心。
4. 策略选择 `rt+numa`。
5. Protected 采集时，系统会把共置负载迁移到 NUMA co-tenant 核心，并执行 RT。

## 11. 安全注意事项

- 不确定时先使用 dry-run。
- 执行策略前确认 PID 和 TID 属于自己的 vLLM 服务。
- stress-ng、zstd、sqlite、memcached 等负载可能占用大量 CPU/I/O，实验结束后及时停止。
- 如果发现性能异常，优先检查遗留负载。
- 在共享服务器上执行 RT 或 NUMA 隔离前，最好确认不会影响其他用户作业。
